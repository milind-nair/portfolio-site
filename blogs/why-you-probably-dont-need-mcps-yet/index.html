Why You Probably Don’t Need MCPs (Yet)

Picture this: You’re building an AI app. You want it to check the weather, send emails, maybe query your database.

Picture this: You’re building an AI app. You want it to check the weather, send emails, maybe query your database.

The hot new thing everyone’s talking about? MCP - the Model Context Protocol.

But here’s the thing most developers are missing: you probably don’t need it.

Let me explain why, and what you should use instead.

The Problem MCP Actually Solves

Think of MCP like a universal translator for AI models and tools.

Without it, connecting models to tools looks like this:

  • OpenAI → your database (custom code)
  • OpenAI → Slack (different custom code)
  • OpenAI → email service (yet more custom code)
  • Anthropic → your database (another custom integration)
  • Anthropic → Slack (another integration)
  • And so on…

With MCP, you write the integration once. Every model that “speaks MCP” can connect automatically.

It’s solving what engineers call the M × N problem:

  • M models × N tools = potentially M×N integrations
  • MCP reduces this to just M + N integrations

Sounds amazing, right?

Here’s the Reality Check

Most developers don’t actually have an M × N problem.

You’re probably building with:

  • One primary AI model (GPT-4, Claude, whatever)
  • A handful of specific tools (your API, database, email service)

That’s a 1 × N problem, not M × N.

For 1 × N, writing simple function/tool calls is faster, clearer, and way easier to debug than implementing an entire protocol.

What Actually Covers Your Needs

Modern AI APIs already solved this. They all support “tool calling” (some call it “function calling”).

Here’s what you get out of the box:

  • Structured outputs in clean JSON
  • The AI decides when to call your tools
  • Consistent error handling patterns
  • Similar patterns across OpenAI, Anthropic, Google (though each has their own API format)

No protocol needed. No extra complexity.

How Smart Frameworks Already Handle This

Frameworks like LangChain, CrewAI, Agno, and Autogen figured this out ages ago.

They use thin abstraction layers instead of heavy protocols.

Quick Example with LangChain:

from langchain_core.tools import tool

@tool
def get_weather(city: str, units: str = "celsius") -> str:
    """Fetch current weather for a city."""
    # Your weather API logic here
    return f"Weather in {city}: 22°{units[0].upper()}"

@tool
def send_email(recipient: str, subject: str, body: str) -> str:
    """Send an email to a recipient."""
    # Your email sending logic here
    return f"Email sent to {recipient}"

Now watch the magic:

from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic

tools = [get_weather, send_email]

# Works with OpenAI
openai_model = ChatOpenAI(model="gpt-4").bind_tools(tools)

# Same tools work with Anthropic
anthropic_model = ChatAnthropic(model="claude-4-sonnet").bind_tools(tools)

# No provider-specific code needed
response = openai_model.invoke("What's the weather in Paris?")

This is the 1 × N solution in action:

  • Define tools once
  • Framework handles different providers
  • Way simpler than a full protocol

CrewAI and Autogen follow similar patterns. They all solve the problem without the heavyweight approach.

When You Actually Need MCP

MCP makes sense in specific scenarios. But they’re rarer than you think.

1. You’re Building a Platform

Creating a marketplace where multiple AI models need access to multiple third-party tools? MCP’s standardization pays off here.

2. You’re a Tool Vendor

Companies like Slack or Notion benefit from implementing MCP once instead of custom integrations for every AI model.

3. You Have True M × N Complexity

Genuinely supporting 5+ AI models across 10+ tools in production? Now the integration matrix gets messy without standardization.

4. You’re Playing the Long Game

If your roadmap includes many models and tools over time, MCP might save future headaches.

But honestly? Most startups and individual projects never reach this complexity.

The Simpler Path Forward

Here’s what actually works for most developers:

Start with your LLM’s native tool calling

  • Pick one provider and use their API directly:
# OpenAI approach
from openai import OpenAI

client = OpenAI()
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get weather for a city",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string"}
            }
        }
    }
}]
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "What's the weather in Paris?"}],
    tools=tools
)

Add a thin abstraction if needed

  • Want to switch providers easily? Use an existing framework that already solved this:
# LangChain handles the provider differences for you
from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """Get weather for a city."""
    # Your logic here
    return f"Weather in {city}: sunny"

# Same tool works with different providers
openai_model = ChatOpenAI(model="gpt-4").bind_tools([get_weather])
anthropic_model = ChatAnthropic(model="claude-4-sonnet").bind_tools([get_weather])

Don’t over-engineer

  • Begin with one model and essential tools
  • Add complexity only when the problem demands it

This approach is:

  • Faster to ship
  • Easier to debug
  • More maintainable
  • Handles 90% of real use cases

The Bottom Line

MCP solves a real problem. But it’s a problem most developers don’t have yet.

Start simple. Ship fast. Add complexity only when the problem forces your hand.

Your users will thank you for the working product, not the elegant architecture they’ll never see.
