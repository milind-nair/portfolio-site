<p><strong>Amazon’s own playbook describes exactly how to prevent the outages it’s now having.</strong></p><p>This week, Amazon called an emergency engineering meeting over a “<a href="https://www.ft.com/content/7cab4ec7-4712-4137-b602-119a44f771de">trend of incidents</a>” that has been quietly degrading the reliability of its retail site. The internal briefing note flagged “Gen-AI assisted changes” and a “high blast radius” as contributing factors. A six-hour outage earlier this month left customers unable to complete transactions or check account details.</p><p>The person who called the meeting, senior vice-president Dave Treadwell, told staff bluntly: “the availability of the site and related infrastructure has not been good recently.” The meeting, normally optional, was made mandatory.</p><h3>AWS Wrote the Playbook</h3><p>The blast radius language in that memo is worth sitting with, because AWS literally published a public playbook on how to contain deployment blast radius.</p><p>The <a href="https://aws.amazon.com/builders-library/automating-safe-hands-off-deployments/">Amazon Builders’ Library</a> describes a deployment architecture built around one principle: limit the scope of any single change reaching production. Code merges trigger a pipeline that runs changes through alpha, beta, and gamma pre-production environments before anything touches real customers. Then production deployments begin with a one-box stage, pushing to a single container or virtual machine first, exposing at most ten percent of traffic to the new code. Rolling deployments replace at most 33% of the fleet at a time. Automatic rollback fires when fault rates, P99 latency, CPU, or memory cross defined thresholds. Between each regional wave, bake time lets the system breathe, monitoring for slow-burning issues before promoting to the next stage.</p><p>The entire <a href="https://aws.amazon.com/builders-library/going-faster-with-continuous-delivery/">continuous delivery program</a> was built after Amazon discovered that engineers were spending 14 out of every 16 days just waiting – for builds, deployments, and test runs. The automation ate that waste. What it produced was a system where developers could merge code and move on, trusting the pipeline to get the change to production safely without anyone watching dashboards at midnight.</p><p>That system exists specifically to stop bad changes from spreading. The memo about AI-related outages flagged a high blast radius as the problem.</p><p>Something is getting through.</p><h3>What the Pipeline Cannot See</h3><p>In December, a 13-hour outage hit an AWS cost calculator after engineers used the company’s own <a href="https://www.ft.com/content/7cab4ec7-4712-4137-b602-119a44f771de">Kiro AI coding tool</a> to make changes to the environment. Rather than updating the existing setup, the AI tool opted to delete and recreate it entirely. The code it produced was coherent. It passed review. The intent was just wrong.</p><p>This is where the safety model has a gap. The AWS deployment pipeline was designed around a very specific assumption: that by the time a change is merged, a human has read it and understood what it does. The code review is described in the Builders’ Library as “the last manual review and approval that a code change receives from an engineer before being deployed to production.” The checklist they use asks reviewers to confirm that the change can be safely rolled back, that all dependencies are already in production, and that no alarms will fire unexpectedly.</p><p>That checklist was written for changes that humans wrote. AI-assisted code introduces a different kind of risk. The changes look reasonable. They follow conventions. They often pass unit and integration tests. The failure mode is not a typo or a missed edge case. It is a misunderstanding of intent that only becomes visible when the change runs against production load, production data, or production infrastructure that the pre-production environment did not perfectly replicate.</p><p>The pipeline’s rollback mechanisms kick in after deployment. They are very good at detecting that something is wrong. They are not designed to detect that a change was conceptually correct but operationally dangerous before it ships.</p><h3>The Fix Amazon Chose</h3><p>Amazon’s immediate response is to require senior engineer sign-off on any AI-assisted changes before they enter the pipeline. Junior and mid-level engineers no longer have the autonomy to merge AI-generated code without that additional layer of review.</p><p>That is a reasonable short-term guardrail. But it raises a harder question.</p><p>A senior engineer reviewing code they wrote, or code their team produced over several hours, brings a lot of context to that review. They know what the change is supposed to do. They can reason about what happens if it goes wrong. They have the mental model to spot something that looks fine but will behave badly under load.</p><p>The same senior engineer reviewing AI-generated code in a standard pull request has less of that context. The code is fluent and well-structured. The AI did not leave the kinds of fingerprints that signal “this might be wrong.” The reviewer is being asked to audit intent in a change they did not write, produced at a speed and volume that human engineers do not naturally match.</p><p>Does adding a senior reviewer to that process actually catch the class of errors that caused these outages? Or does it just add a step that provides the appearance of oversight without the substance of it?</p><p>Amazon’s deployment infrastructure is among the most sophisticated ever built. The meeting this week is not really about AI tools or deployment pipelines. It is about whether the human judgment that the whole system depends on can keep up with the rate and character of change that AI-assisted development produces.</p><p>That answer is not obvious yet. And Amazon, of all companies, knows how much that answer matters.</p>
